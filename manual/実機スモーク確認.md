# 実機スモーク確認

VRChat（PC）で、プリセット切替まわりが壊れていないことを短時間で確かめる手順です。
**4ケースで4〜6分**を想定しています。

この手順が必要なのは、開発側の自動テストでは**実ネットワーク遅延下での挙動**を確認できないためです。
判定ロジックはライセンス不要の自動テストで確認していますが、それは「規則どおりに動くこと」までで、
「実際のワールドで気持ちよく動くこと」は確認できません。

各バージョンの確認状況は [バージョン対応表](README.md#動作確認済みの組み合わせ) に記録しています。

**Case 1〜4はプリセット切替まわりだけを見ます。** 照明連携（合成方式・反射方式・Additive受光）の見え方は、[実機確認: R30の照明連携](実機確認_R30照明連携.md) にあります。Lighting Engineを導入したワールドは、下の [Lighting Engineを実機で確認する](#lighting-engineを実機で確認する) も行ってください。プリセットの動作範囲をローカルにしたワールドは、[プリセットがローカルのときの所有権と回転を2人で確認する](#プリセットがローカルのときの所有権と回転を2人で確認する) も行ってください。

## 準備

1. MirrorBallLightのPrefabを配置したテスト用ワールドを用意します
2. **見た目が明確に違う3つのプリセット**を作ります。ここでは **A / B / C** と呼びます
   - 色・明るさ・回転速度のように、一目で違いが分かるものにしてください
   - 「現在値を選択プリセットへ保存」で作れます
3. Controllerの **クロスフェード時間** を **3秒程度** にします
   - 短いと「遷移中に操作する」が間に合いません
4. A / B / C を切り替えるボタン（`apiPresetIndex` を書いて `RequestSelectPreset` を呼ぶ等）を用意します

各ケースは**Aから始めてください。**

## 記録の書き方

各ケースについて、合格・不合格・未実施のいずれかを記録します。
**「たぶん大丈夫」は不合格として扱ってください。** 判断がつかなければ、もう一度やり直します。

---

## Case 1: 予約が効くこと

| | |
| --- | --- |
| **目的** | 遷移中の要求が1件だけ覚えられ、遷移後に実行されること |
| **設定** | 「切替中の要求を1件だけ予約」を **ON** |

**操作**

1. A の状態から **B** を選ぶ（クロスフェードが始まります）
2. **フェードが終わる前に C** を選ぶ
3. フェードが終わるまで待つ

**合格条件**

- 最終的に **C の見た目**になっている
- B へのフェードは最後まで進み、途中で C へ飛んだりしない
- ちらつき・一瞬の暗転・逆戻りが無い

---

## Case 2: 予約が悪さをしないこと

| | |
| --- | --- |
| **目的** | 設定をOFFにすれば、これまでどおり無視されること |
| **設定** | 「切替中の要求を1件だけ予約」を **OFF** |

**操作**

1. A の状態から **B** を選ぶ
2. **フェードが終わる前に C** を選ぶ
3. フェードが終わるまで待つ

**合格条件**

- 最終的に **B の見た目**のまま止まっている（**C へ移らない**）
- フェード終了後に、勝手にもう一段の切替が起きない

**このケースが不合格なら、既定の挙動が変わってしまっています。**
すぐに開発側へ知らせてください。

---

## Case 3: 電源を切ったら予約も消えること

| | |
| --- | --- |
| **目的** | 消灯後に、消したはずのタイミングで切り替わらないこと |
| **設定** | 「切替中の要求を1件だけ予約」を **ON** |

**操作**

1. A の状態から **B** を選ぶ
2. フェードが終わる前に **C** を選ぶ（予約が入ります）
3. **すぐに電源をOFF**にする
4. 数秒待ってから電源をONにする

**合格条件**

- ONにした直後に **C へ勝手に切り替わらない**
- 操作を受け付けなくなったり、見た目が壊れたりしない
- この後 A / B / C を選べば、普通に切り替わる

---

## Case 4: 動作範囲を変えたら予約が残らないこと

| | |
| --- | --- |
| **目的** | ローカル専用とグローバル同期を切り替えたとき、古い予約が発火しないこと |
| **設定** | 「切替中の要求を1件だけ予約」を **ON** |

**操作**

1. A の状態から **B** を選ぶ
2. フェードが終わる前に **C** を選ぶ（予約が入ります）
3. **プリセットの動作範囲**を切り替える（ローカル ↔ グローバル）
4. 数秒待つ

**合格条件**

- 古い予約（C）が発火しない
- 切り替えた後、A / B / C を選べば普通に切り替わる

---

## 複数人で確認する場合（任意）

グローバル同期を使うワールドでは、次も確認すると安心です。

- **プリセットの動作範囲がグローバル**のとき、片方が Case 1 を行い、もう片方の画面でも
  同じ順序で切り替わること
- 後から参加した人の見た目が、既にいる人と一致すること

**予約そのものは同期されません。** 予約した人の手元で次の切替が始まった時点で、
その切替が全員へ同期されます。片方の画面だけ「予約待ち」になることは正常です。

## 設置型パネルを2人で確認する

この手順は実VRChatの確認用です。ClientSimの結果で合格にはしません。
PCのDesktopとVRを用意し、2人が同じ検証インスタンスに入ります。操作する人をA、確認する人をBとします。
最初にワールド版、端末、人数、電源とプリセットの操作範囲、Controller所有者を記録してください。

### 準備

- 最新パッケージを専用の検証ワールドに導入し、Controllerへ見た目が違う3つのPresetを登録してライブプリセットを有効にします。
- ControlPanelの参照先Controllerを設定し、POWERとPREV／NEXTを前面から操作できるように配置します。壁に密着させた配置も含めます。
- LocalとGlobalのパネル設定はUnityのInspectorで変更します。ControlPanelの操作範囲は参照先Controllerの電源とプリセットへ反映されるため、両方を記録してください。
- エラーの発生元を調べるときはVRChatを `--enable-udon-debug-logging` 付きで起動し、SDKのRuntimeログと再現手順を残します。公開用の記録から個人名やインスタンスIDを除いてください。

### 確認項目

| ケース | 操作 | 合格条件 |
| --- | --- | --- |
| Localの電源とプリセット | Local設定の検証ワールドで、AがPOWER、PREV、NEXTを操作する。続いてBも操作する | 各自の電源と演出だけが変わり、相手側へ波及しない。表示名は各自の現在のPresetに追従する |
| Globalの操作権限 | Global設定で、Controller所有者がPOWERとPREV／NEXTを操作する。非所有者も操作を試す | 所有者の操作が両者へ反映される。非所有者には操作不可の状態が表示され、共有状態を書き換えない |
| 途中参加と所有者交代 | 所有者が任意の電源・Presetを選び、Bが退出して再参加する。次に所有者が退出し、残った人が操作する | 再参加者が現在の共有電源・Presetへ追従する。所有者交代後も新しい所有者が操作でき、操作不能のまま残らない |
| Desktop／VRの前面操作 | DesktopとVRそれぞれで、壁に密着したパネルのPOWERとPREV／NEXTを前面から押す | 狙ったボタンが反応し、隣のボタンや壁への誤操作がない。光点の飛び・回転の急変・Udon例外がない |

Global時の光点は各PCで同じ時刻に撮影して比べてください。回転の一時停止、フェード中、電源の再投入も含めます。
例外が出たケースは合格にせず、ログからBehaviourを特定して再検証します。

記録欄には各ケースの「合格／不合格／未実施」、確認日、端末、人数、所有者、ログの有無を記入します。
ワールドを準備したことや、1人の画面が正常なことだけで複数人同期を確認済みにしないでください。

## プリセットがローカルのときの所有権と回転を2人で確認する

この手順も実VRChatの確認用です。ClientSimでは「所有者でない人のローカル操作で所有権が移らないこと」までを確かめていますが、
**他の人の操作を受け取った側の見え方**と、**所有者が実際に退出したとき**の挙動は確かめられません。

対象は、ライブプリセットを使い、プリセットの動作範囲がローカル、電源の動作範囲がグローバルのワールドです。
この設定を使わないワールドでは、この節は未実施で構いません。

### 準備

- Controllerを「ライブプリセット使用・プリセットの動作範囲＝ローカル・電源の動作範囲＝グローバル」にし、**回転速度の違うプリセットを3つ以上**登録します。
- 操作パネル（またはUI Bridgeのボタン）を置きます。
- 演出シーケンスを1つ置き、ローカル範囲で動くようにします。
- 先に入室した人（Controllerの所有者）をA、後から入室した人をBとします。所有者はVRChatのデバッグ表示（UdonのNetworking表示）で確かめます。

### 確認項目

| ケース | 操作 | 合格条件 |
| --- | --- | --- |
| T1 ローカル操作で所有権が移らない | Bがパネルでプリセットを「次へ」で2回切り替える | Aの画面で、Aのプリセット表示と回転速度が変わらない。Controllerの所有者がAのまま |
| T2 他の人の電源操作で手元のプリセットが変わらない | Bがプリセットを切り替え、クロスフェード中にAが電源をOFF→ONする | Bの画面で、Bのプリセット表示が切り替え先のままで、クロスフェードが切り替え先で終わる。消灯・点灯の瞬間に回転角が飛ばない |
| T3 所有者が退出してもシーケンスが止まらない | Bがローカル範囲のシーケンスを再生し、再生中にAがワールドから退出する | Bの画面で、シーケンスが止まらず、次のステップへ進み続ける |
| T4 Engineが回転を管理するときの滑らかさ | Lighting Engineで「回転を管理」を使うワールドで、AとBがそれぞれ本体と壁の光点を見る | 本体と受光面の光点の回転が、カクつかずに滑らかに見える |

**この設定では、壁の光点の位置は人によって一致しません。** 回転速度が人ごとに違いうるため、回転角も人ごとに持ちます。
光点の位置が2人で違うことを理由に不合格にしないでください。電源のON/OFFは全員に届きます。

T4はEngineを導入していないワールドでは未実施で構いません。記録の書き方は「設置型パネルを2人で確認する」と同じです。

## Lighting Engineを実機で確認する

Lighting Engineは、受光面Shaderとは別の経路で壁・床・天井の実形状へ光点を置きます。
配置はRaycastとGPU Instancingで各自のPCが計算するため、**Unity Editor・ClientSimで見えたことを実機の合格に読み替えません。**
Engineを導入していないワールドでは、この節は未実施で構いません。

### 準備

- 導入ウィンドウ（Tools → MirrorBall Light → Lighting Engineを導入）で受光対象を登録し、「一覧の対象へLighting Engineを設定」を実行した状態で、ワールドをアップロードします。
- 受光対象の中に、**白っぽい面・はっきり色の付いた面・黒っぽい面**を1つずつ含めます。受光面の色の効き方を見分けるためです。
- 登録していない柱や家具を1つ、ボールと壁の間に置きます。遮蔽の確認に使います。
- Controllerの「光点の形状」を**四角以外**（丸・★・♥など）にしておきます。Engineの光点がControllerの形に追従しているかを見分けるためです。
- 確認する人のローカル品質（LOW／MED／HIGH／ULTRA）と、Photo Modeの有効・無効を記録します。

### 確認項目

| ケース | 操作 | 合格条件 |
| --- | --- | --- |
| E1 配置と遮蔽 | 電源を入れ、ボールを回転させたまま壁・床・天井を順に見る | 光点が登録した面の上に乗り、空中や面の裏に浮かない。未登録の遮蔽物の陰に光点が出ない。鏡・動画スクリーン・テキストの上に光点が出ない（除外した場合） |
| E2 受光面の色と形 | 白・色付き・黒の面を見比べる。次に「受光面の色の影響」を0にしたビルドでも見る | 色付きの面では光点にその色が付き、黒い面では暗い。影響0では白い光点になる。光点の形がControllerで選んだ形と一致する。斜めの面では、受光面Shaderの光点と同じように入射の方向へ伸び（R37.1から）、受光面の端からはみ出さない |
| E3 ローカル品質 | 自分のローカル品質をLOWとULTRAで切り替える。もう1人は変えない | 光点の数が自分の画面だけで変わり、相手の画面は変わらない。OFFで光点が消える |
| E4 Photo Mode | Photo Modeを有効にしたビルドで撮影カメラを開く・閉じる | 撮影カメラの画だけ光点が増える。通常の画面は撮影カメラを開く前後で光点の更新間隔と寿命が変わらない |
| E5 音反応と回転 | AudioLinkのあるワールドで曲を流し、7ジャンルの演出プリセットと回転パターン（Beat Syncなど）を切り替える | Bassで光点サイズ、Highで密度、Kickでフラッシュが変わる。Beat Syncは指定BPMで拍に合う。AudioLinkが無い構成でも電源・回転が止まらない |
| E6 複数人 | 2人が同じインスタンスで同じ壁を同時刻に撮影する。途中参加・所有者交代もCase 1〜4と同じ手順で行う | ボールの回転は共有されるため、両方の画面に出ている光点どうしは同時刻に同じ位置にある。どのFacetの光点を出すかは各自の画面で選ぶので、出ている光点の組は人によって違うことがあり、これは正常（プリセットの動作範囲がローカルでライブプリセットを使う設定は、回転角が人ごとなので対象外）。品質の違いによる光点数の差は正常。途中参加者の画面にも光点が出る。Udon例外が出ない |
| E7 光点の流れ | ボールを一定回転（例: Controllerで毎秒3°、またはEngineの回転パターン「一定回転」）にして、壁の光点を1分ほど見続ける | 光点が回転の向きへ連続して流れる。止まったまま別の場所へ入れ替わったり、撃ち直しのたびに跳んだりしない。光の円錐から出ていく光点は、徐々に暗くなって消える。回し続けても、光点が光の当たる範囲の片側（光から出ていく側）に寄ったり、重なったりしない（R37.1から） |
| E8 光点の大きさと面の縁 | Engineの `debugClipPath` をONにしたビルドで、ボールに近い壁と遠い壁、天井の梁や柱の角に当たる光点を見る | ボールに近い面の光点は小さく、遠い面では大きい。光点は緑で表示される（深度で切っている。鏡の中だけ黄色）。梁・柱の角・段差の縁から光点がはみ出して宙に浮かない。HMDでも両眼で同じように切れている（R37.2から） |

HMDでも同じケースを見ます。**両眼で光点の位置がずれて見える、鏡の中だけ光点が消える**は不合格です。
Photo Modeの512個はPCだけの配置予算で、通常の画面や鏡には増やしません。通常の画面で光点が増えたら不合格です。

記録欄には、ローカル品質、Photo Modeの有無、連携パッケージの版、ケースごとの「合格／不合格／未実施」、確認日、端末、人数を書きます。
[バージョン対応表](README.md#動作確認済みの組み合わせ)の実機欄を「済」にするときは、この節のどのケースまで見たかも注に書いてください。

## 不合格だったときは

再現手順（どのケースか、クロスフェード時間、動作範囲、人数）を添えて、
[Issue](https://github.com/BossNovice/VRC_MirrorBallLight_Manual/issues) へ報告してください。
